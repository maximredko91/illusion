# Иллюзион (Illusion)

Formerly named "Сеанс" (Seance) — renamed 2026-08-23. Package, classes, and all in-app strings were updated to match; see git history around this date if a stale "Seance"/"Сеанс" reference turns up somewhere this pass missed.

Android media-center app (Kotlin, Jetpack Compose/Material3, `com.illusion.app`, minSdk 26 / targetSdk 37 / compileSdk 37). Streams video directly from an SMB share on a home NAS ("Netcraze Ultra" router) — no download required for playback. Full spec lives in the conversation history / ask the user for the ТЗ if needed; this file tracks durable architecture and status.

## Architecture

MVVM, package-by-feature, **no DI framework** — `IllusionApplication.kt` manually wires all singletons. This is intentional (user prefers minimal abstraction, not an oversight).

- `data/local` — Room: `SmbSourceEntity`, `MediaItemEntity`, `WatchProgressEntity`, `FavoriteEntity`, `ThumbnailSpriteEntity` + DAOs
- `data/smb` — `SmbClient`/`SmbConnection` (wraps `smbj` 0.14.0), `SmbCredentialStore` (EncryptedSharedPreferences, never Room), `StableIdGenerator`. Read-only for scanning/playback; `SmbConnection.mkdirs`/`openOutputStream`/`openRandomAccessFileForWrite`/`deleteFile` exist solely for the developer-only add-media flow below.
- `data/nfo` — Kodi-style `.nfo` XML parser (`NfoParser`) + writer (`NfoWriter`, developer-only add-media flow only)
- `data/tmdb` — `TmdbClient` (developer-only add-media flow only - the only place this app calls the internet for metadata)
- `data/security` — `DevAccessStore`, the password gate for the add-media flow
- `data/player` — custom Media3 `SmbDataSource`/`SmbDataSourceFactory`, positional reads via `SmbRandomAccessFile` (no local download)
- `data/scan` — `LibraryScanner`, `ThumbnailGenerator`, `SmbMediaDataSource`
- `work` — WorkManager: `LibraryScanWorker`, `WorkScheduler`, `UploadWorker` (developer-only add-media flow). No more `ThumbnailGenerationWorker` (removed 2026-08-30) - scrub-preview sprites now generate lazily via `IllusionApplication.generateThumbnailIfMissing`, see the note under "Implementation status vs spec" below.
- `ui/*` — per-feature screens; `ui/player/*` is the most fully-built subsystem (gestures, gradient overlay, scrub thumbnails, PiP, GPU sharpen shader via Media3 Effects); `ui/addmedia/*` is developer-only, see below

## Key decisions (don't relitigate without reason)

- Custom Media3 `DataSource` over SMB, not download-then-play — needed for streaming/seeking.
- **DTS / TrueHD (and AC3/E-AC3 fallback) audio** (added 2026-09-14) — now decoded by the app's own FFmpeg build through `FfmpegAudioRenderer` (codec names as in Media3's decoder_ffmpeg: `ac3`/`eac3`/`dca`/`truehd`; TrueHD context is rebuilt on reset like Media3 does). The renderer sits after the platform one, so the phone's own `c2.dolby.eac3.decoder` still takes AC3/E-AC3/E-AC3-JOC (verified on Аватар: AC3 5.1 → Dolby decoder) and HDMI passthrough on the TV box still wins; FFmpeg only takes what nothing else can — on this phone DTS and TrueHD (no platform decoder, checked in media_codecs*.xml). **DTS and TrueHD verified on-device 2026-11-15** on FFmpeg-generated 5.1 test files (`-c:a dca -strict -2` / `-c:a truehd -strict -2`, H.264 video, .mkv): sound confirmed by the user, and logcat showed no platform audio codec instantiated at all while a 48 kHz 6-channel PCM AudioTrack was opened - i.e. the FFmpeg renderer took both. Synthetic encodes only: a real DTS-HD MA / Atmos-in-TrueHD remux track hasn't been tried. The old Media3 decoder_ffmpeg AAR route (`scripts/build_ffmpeg_extension.sh`, `illusion.ffmpegExtension.aarPath`) is superseded.
- **Own FFmpeg *video* decoder** (added 2026-09-13, `data/player/ffmpeg/*`, `src/main/cpp/ffmpeg_video_jni.cc`) — separate from the audio extension above. LGPL FFmpeg n8.1.2 is built on a Linux runner by `.github/workflows/ffmpeg-android.yml` (manual dispatch, runs `scripts/build_ffmpeg_android.sh`: decoders mpeg4/msmpeg4v1-3/h263/wmv1-3/vc1/mpeg1-2/wma, demuxers matroska/asf/avi) and the resulting shared `.so` + headers are committed per ABI under `app/src/main/cpp/ffmpeg/` — FFmpeg's configure/make can't run on this Windows machine without MSYS2/WSL, so never try to build it locally; re-dispatch the workflow and re-download the artifact instead. Flat SONAMEs (sed on `ffbuild/config.mak`) are required or Android's loader can't find `libavutil.so.60` inside the APK. AGP packages the IMPORTED libs via CMake, so they must NOT also be in `jniLibs`. `FfmpegVideoRenderer`/`FfmpegVideoDecoder` follow Media3's own libvpx extension (bytecode + 1.11.0 sources checked). `IllusionRenderersFactory` puts the renderer first in Авто/Программный, last in Аппаратный; in Авто it reports `FORMAT_EXCEEDS_CAPABILITIES` for MPEG-2/H.263 so the platform decoders still win those, and only takes MPEG-4 ASP/MS-MPEG4/VC-1. Verified on-device on a DivX 5 `.avi` (Клиника S01E01): clean picture where `c2.android.mpeg4` showed macroblocks. Sharpen: Media3 effects still never reach FFmpeg-decoded frames (GL effects only run on MediaCodecVideoRenderer's VideoSink), so since 2026-09-19 the decoder sharpens them itself - `sharpenPlane` in `ffmpeg_video_jni.cc` applies the same unsharp-mask kernel as `SharpenEffect`'s fragment shader (out = c + amount * (4c - left - right - up - down)) to the luma plane while the frame is copied into the window buffer, in 8.8 fixed point, chroma untouched. Strength arrives as a live provider lambda (`IllusionRenderersFactory(sharpenAmountProvider)` -> `FfmpegVideoRenderer` reads it per rendered frame -> `nativeSetSharpen`), mirroring how `SharpenEffect` reads its own amount, so toggling sharpen mid-playback needs no reload on this path. **Not verified on-device.** Two sharp edges hit while shipping it: (1) R8 strips `VideoDecoderOutputBuffer.initForYuvFrame/initForPrivateFrame/data/decoderPrivate` because only JNI reaches them by name → keep rule in `proguard-rules.pro` (Media3 extensions ship it as a consumer rule, this app doesn't depend on them); the first release build aborted the whole app with `NoSuchMethodError` inside `nativeInit`. (2) Drawing via `ANativeWindow_lock` connects the Surface as a CPU producer for the Surface's whole life — `ANativeWindow_release` doesn't disconnect and the NDK has no public disconnect — so MediaCodec/GL effects on the same Surface afterwards fail with `EGL_BAD_ALLOC (0x3003)`. Fixed by `PlayerViewModel.videoSurfaceGeneration`: once an `ffmpeg-*` decoder initialized, the next player swap/source change bumps it and `PlayerScreen` rebuilds its `PlayerView` via `key()`. Don't "simplify" that away.
- **.wmv playback** (added 2026-09-13, `data/player/asf/*`, `ffmpeg/FfmpegAudio*`, `src/main/cpp/ffmpeg_audio_jni.cc`) — deliberately NOT via the libavformat bridge from the Cues idea below: `AsfExtractor` is a plain Kotlin Media3 `Extractor` (ASF header objects, fixed-size data packets, payload-fragment reassembly, Simple Index seeking; layout taken from FFmpeg's `asfdec_f.c`, GUIDs cross-checked with `asf_tags.c`), registered first in `IllusionExtractorsFactory` (which must keep forwarding DefaultMediaSourceFactory's subtitle-parser settings to the wrapped `DefaultExtractorsFactory`). SMB streaming, buffering and seeking stay Media3's own; only decoding goes to FFmpeg — WMV1-3/VC-1 through `FfmpegVideoRenderer`, WMA v1/v2/Pro through the new `FfmpegAudioRenderer` (native side interleaves planar float itself, no libswresample; WAVEFORMATEX block_align/bit depth ride in `initializationData[1]`, see `WindowsMediaMimeTypes`). Covered by `AsfExtractorTest` on a real FFmpeg-muxed fixture (tracks, 60/87 samples, timestamps, byte-exact reassembly, index seek). Two gotchas hit: `ParsableByteArray` crashes in plain JVM tests unless `setShouldEnforceLimitOnLegacyMethods(true)` is called first (its Robolectric probe NPEs); and inside an inner class implementing `SeekMap`, a bare `durationUs` resolves to `getDurationUs()` itself → StackOverflowError. Verified on-device 2026-09-14 with an FFmpeg-muxed WMV2+WMA2 test file on the NAS: `ffmpeg-wmv2` + `ffmpeg-wmav2` in the video info, correct picture, seeking by the Simple Index resumes playing within ~0.5 s. WMV3/VC-1 and WMA Pro still unverified on a real file.
- **DLNA casting to a TV** (built 2026-09-19, `data/cast/*` + `ui/player/CastPanel.kt`/`CastState.kt`) — replaces the long-standing "Cast button is a disabled stub" note. Chromecast/Cast SDK is still NOT implemented (a Chromecast would also need the Cast SDK on top, and can't decode much of this library anyway); DLNA was chosen instead because it needs no Google dependency and the TVs on this network speak it. How it works: `LocalStreamingServer` now binds every interface instead of loopback only (a renderer fetches over the LAN), guarded by a per-instance random `token` every request must carry — that token is the only thing standing between this bridge and an open NAS share for the whole network, don't drop it. `StreamingService.lanStreamUrl` builds the LAN-addressed form, reading this device's IPv4 from `ConnectivityManager`'s active-network `LinkProperties` (NOT by walking NetworkInterface — with a VPN or tethering up, enumeration returns addresses the TV can't reach). `DlnaDiscovery` is hand-rolled SSDP (M-SEARCH ×3 on one socket, multicast lock held, then a GET per device for its description XML → friendlyName + AVTransport controlURL, resolved against `URLBase` when present); `DlnaController` speaks AVTransport SOAP by hand (SetAVTransportURI with DIDL-Lite metadata, Play/Pause/Stop/Seek REL_TIME, GetPositionInfo/GetTransportInfo). No Cling/jUPnP — they bring a whole device stack and their own HTTP servers for what is two operations here. Cast state is a SEPARATE `StateFlow` (`PlayerViewModel.castState`), deliberately not a field on `PlayerUiState`, which `playItem`/`playTrailerItem` rebuild from scratch. Position comes from polling every 2 s (UPnP eventing would need a callback HTTP server) and feeds watch progress, so stopping a cast leaves the item resumable; stopping also seeks the local player to where the TV got to. Needs `CHANGE_WIFI_MULTICAST_STATE` (added). Parsing is covered by `DlnaParsingTest`. **Google Cast added on top 2026-09-19** (`data/cast/GoogleCastController.kt`/`GoogleCastOptionsProvider.kt`, contributed via ChatGPT and verified by the user on a Xiaomi TV Box S 2nd Gen): that box answers Google Cast only, not DLNA, which is what sent DLNA discovery home empty-handed on the first real test. Uses Google's Default Media Receiver (no receiver registration), MediaRouter for discovery and `RemoteMediaClient` for load/play/pause/seek; the picker lists Cast and DLNA devices together, each labelled with its protocol. `MainActivity` warms `CastContext` in `onCreate` inside a `runCatching` so a device without Play services still gets the local player and DLNA. `GoogleCastOptionsProvider` is instantiated by name from manifest metadata, so it needs its own R8 keep rule. `LocalStreamingServer` answers OPTIONS and sends CORS headers because the Cast receiver is a web app; the token check is unchanged. No transcoding - the receiver's own codec support decides what plays. DLNA itself is still unverified against a real renderer.
- Adaptive buffering is one-shot at player creation (bandwidth estimate), not continuous — swapping `LoadControl` on a live `ExoPlayer` risks `Allocator` desync.
- GPU sharpen shader implemented against real decompiled Media3 1.11.0 bytecode (`javap` on Gradle-cached `.class` files), not guessed from docs — do this for other fast-moving Media3 Effects / newer Android platform APIs too.
- Dolby Vision Profile 7 (FEL, dual-layer) enhancement-layer detail can never be composited by this app, on the phone *or* the Xiaomi TV Box target — verified by decompiling media3-container 1.11.0's `DolbyVisionConfig.java` (only parses `dvcC`/`dvvC` for a codec string, never reads `el_present_flag` or an EL track) and cross-checking AOSP's HDR docs (BL+EL concatenation needs a vendor `MediaExtractor`, not available through ExoPlayer's Java extractors, which is all this app's `SmbDataSource` pipeline uses). Not a decoder-capability gap on any specific device — it's architectural. Player now surfaces the DV profile number in its diagnostic overlay and a plain-language warning when Profile 7 is detected, rather than attempting compositing.

## Fixed bug — Details screen status bar bleed-through (resolved 2026-08-18)

`DetailsScreen`'s fanart backdrop intermittently rendered behind the (transparent, edge-to-edge) status bar instead of being pushed below it — `Modifier.statusBarsPadding()` measured a correct nonzero inset when logged, but still applied zero effective padding, and this recurred even without any dialog involved (a genuine Compose/OS insets-redispatch race on this device, not app-controlled). Fixed by reading `WindowInsets.statusBars` *and* cross-checking `ViewCompat.getRootWindowInsets` on the real `View` directly, latching onto the largest value either has ever reported (the real status bar height doesn't shrink mid-session, so a regression to a smaller/zero value is always the race), plus a one-shot ~200ms recheck in case the very first frame lands before any real dispatch arrives. Separately, the padding itself had to move to *before* `.verticalScroll()` in the modifier chain — placed after (the original code), it only offset the initial scroll position, so scrolling down let later content (description, cast) pass behind the status bar too. `ui/common/ZoomableImageViewer.kt`'s full-screen poster/fanart `Dialog` had the same class of bug for a different reason — a Compose `Dialog` opens its own separate `Window`, which `MainActivity`'s `enableEdgeToEdge()` doesn't reach, and `DialogProperties.decorFitsSystemWindows` defaults to `true` — fixed by passing `decorFitsSystemWindows = false` (paired with `usePlatformDefaultWidth = false`, per that property's own KDoc recommendation).

## Fixed bug — SMB connection timeout via `ACCESS_LOCAL_NETWORK` (resolved)

`targetSdk = 37` triggers Android's mandatory `ACCESS_LOCAL_NETWORK` runtime permission (https://developer.android.com/privacy-and-security/local-network-permission) — any raw-socket local-network connection (which is exactly what `smbj` does) is silently blocked by the OS until this permission is declared *and* granted at runtime, manifesting as a plain TCP timeout rather than an explicit denial. **Fixed**: `AndroidManifest.xml` declares the permission, and `data/smb/LocalNetworkPermission.kt` + `ui/smbsource/LocalNetworkPermissionGate.kt` request/gate it at runtime, wired into onboarding, SMB add/edit forms, and scan/playback paths.

## Implementation status vs spec (audited 2026-08-16 — re-verify before trusting specific claims, code moves fast)

**Working**: SMB multi-source scanning + Room index, `.nfo` parsing, 4-category model, onboarding + test-connection + scan-progress flow, player core (gestures, gradient bars, scrub thumbnails, resume, external subs, audio-track switching, PiP, immersive mode, autoplay-next, wake lock, error/retry), Material You + day/night, edge-to-edge, Details screen (fanart/poster/metadata/cast-filmography/similar/collections, continue-watching, zoomable poster/fanart), Coil `AsyncImage` sized loading across all screens (grids/carousels/Details no longer decode at full source resolution), functional search, library sort/filter UI, Favorites/History UI, backup export/import, manual rescan only (no periodic auto-rescan - removed 2026-08-30, see below), rename-proof `StableIdGenerator` (hashes source+size+byte samples, not filename), offline downloads (`DownloadsScreen`/`DownloadWorker`/`DownloadEntity`), Settings cache management + SMB source edit, empty states/shimmer/shared-element transitions/haptics, MP4 audio-track title read (`Mp4AudioTrackTitleReader`, `udta/name` box) for "озвучка" display, SMB source form UX (imePadding keyboard fix, password visibility toggle, host/share autofill suggestions), trailer playback (Kodi/TMM `<video>-trailer.ext` or bare `trailer.ext` sibling file, detected during scan and excluded from being indexed as its own item — see `SmbFileRef.isTrailer`/`LibraryScanner`'s `matchesTrailer`, `PlayerViewModel.loadTrailer`, `MediaItemEntity.trailerPath`).

**Decoder mode** (added 2026-09-12) — в самом плеере, не в настройках приложения (перенесено по просьбе пользователя в тот же день): раздел «Декодер» в панели ⚙ плюс иконка-чип быстрого переключения в верхней панели управления. Авто/Аппаратный/Программный (`domain/model/DecoderMode.kt`, `data/player/DecoderModeSelector.kt`). Only *reorders* the platform's decoder list for a MIME type (`MediaCodecSelector` handed to `DefaultRenderersFactory`), never shortens it — a format with a single decoder still plays in every mode, so this changes nothing for MPEG-4 ASP (DivX/XviD), where `c2.android.mpeg4.decoder` is the only option either way; it's for streams a hardware decoder renders with artifacts/green frames. AUTO returns `MediaCodecSelector.DEFAULT`, i.e. byte-identical to every build before the setting existed. Changing it mid-playback triggers `reloadPlayer()` (position/playing state preserved). The diagnostic overlay now also shows the decoder MediaCodec actually instantiated, via `AnalyticsListener.onVideo/AudioDecoderInitialized` + `isHardwareDecoder()`. Проверено на устройстве: Авто/Аппаратный → `c2.qti.avc.decoder`, Программный → `c2.android.avc.decoder`, переключение на лету с сохранением позиции. Две ловушки, пойманные при этом: (1) девятая иконка не влезала в верхнюю панель в портретной ориентации (последняя обрезалась) — в компактном режиме снят Material-минимум 48dp через `LocalMinimumInteractiveComponentSize`, кнопки становятся по 40dp; (2) `playItem`/`playTrailerItem` пересобирают `PlayerUiState` с нуля, и новое поле надо явно переносить, иначе выбор мгновенно откатывался в AUTO на том самом перезапуске плеера, который сам же и вызвал. The app's own FFmpeg video decoder (see Key decisions) plugs into this same setting via renderer order - that's the MX Player-style HW/SW switch the user asked for. Also fixed alongside it: the top bar's controls auto-hide (3.5 s) used to dismiss an open decoder/sleep-timer dropdown mid-choice (`TopGradientBar.onMenuOpenChange` now pauses it).

**Обязательное обновление больше не ждёт периодичности** (fixed 2026-09-20) — жалоба «уведомление приходит, только если проверять вручную». Причина: интервал «Автопроверка обновлений» по умолчанию был 720 ч (раз в месяц), и И on-launch проверка, И `UpdateCheckWorker` просто не ходили в сеть до его истечения; суточный запасной интервал применялся ТОЛЬКО при «Выключено» (`if (autoCheckDisabled) MANDATORY_FALLBACK else intervalHours`), поэтому при «раз в месяц» обязательный релиз оставался невидимым месяц. Теперь разведены две вещи: в сеть ходим не реже раза в сутки при любой периодичности (`minOf(intervalHours, 24)`), а сама периодичность решает, когда показывать ОБЫЧНОЕ обновление - для этого добавлен отдельный таймстамп `SettingsRepository.lastRegularUpdateShownAtMs` (иначе диалог всплывал бы ежесуточно при «раз в месяц»). Обязательное показывается сразу, мимо периодичности, «Выключено» и «Пропустить версию». Заодно дефолт интервала сменён с 720 ч на 24 ч: для беты, которая выходит по несколько раз в день, «раз в месяц» бессмысленно.

**Background update notification** (added 2026-09-15) — `work/UpdateCheckWorker.kt`, scheduled daily (`WorkScheduler.schedulePeriodicUpdateCheck`, KEEP, network-constrained) from `IllusionApplication.onCreate`. Applies the same rules as the on-launch check (`UpdateViewModel.checkForUpdate`): the «Автопроверка обновлений» interval, «Выключено» still letting mandatory releases through at most daily, «Пропустить версию». Keeps its own `lastBackgroundUpdateCheckAtMs` (sharing the on-launch timestamp would suppress the in-app dialog for users with notifications off) and `lastNotifiedUpdateVersionCode` (one notification per release). A failed check doesn't consume the interval. Notification tap puts `UpdateNotifications.EXTRA_SHOW_UPDATE` on the MainActivity Intent → forced check → dialog (skipped when `savedInstanceState != null`, so rotation doesn't re-trigger). **Not verified on-device** — shipped in beta76 without a device connected; the first real notification can only appear once a release newer than the installed build exists.

**Графика экрана описания** (2026-09-20) — из семи предложенных идей пользователь по итогам проверки на устройстве оставил две: **цвет из постера** (`ui/common/PosterAccent.kt` - Palette по копии 96 px, светлота/насыщенность подгоняются под тему, кеш на 64 записи; рисуется подложкой на ВСЮ площадь экрана описания, включая полосу под верхней панелью) и **параллакс** фанарта при прокрутке (отставание 60% + лёгкий наезд). Обе - с отдельными переключателями в Настройках → Оформление, с подписями «что даёт и чем платит», плюс `LocalVisualEffects`; «Экономичный» гасит их поверх галочек. Отклонены после проверки и удалены: Ken Burns («живой фон» - движение незаметно на шапке 188dp), кадр с места остановки вместо постера в «Продолжить просмотр» (спрайт 160x90 растягивался на карточку - «шакальное качество»), волна на двойном тапе в плеере (лишняя, и координаты не совпадали с точкой касания - тап ловится во вложенном слое). Стекло в плеере невозможно в принципе: `SurfaceView` композитится мимо Compose, а переход на `TextureView` стоил бы HDR/DRM/4K (см. `GlassBackdrop`'s own limitation note). **Сильная ловушка, на которую ушло четыре сборки**: верхняя полоса на экране описания залита `colorScheme.surface`, то есть цветом фона экрана, и её скруглённые нижние углы видно ТОЛЬКО потому, что под ними просвечивает цветная подложка. Подрезать подложку по верхнему отступу (казалось бы, «цвет затекает под панель») - значит сделать углы чёрными, и полоса читается прямоугольной; давать полосе свой оттенок - значит получить серую плашку с чёрными уголками. Рабочий вариант: подложка на всю площадь + контент заходит под полосу на высоту скругления (`TOP_BAR_OVERLAP`), тогда её углы ложатся на картинку. Не «чинить» это снова.

**Спрайты превью перемотки крупнее** (2026-09-20) — клетка 160x90→320x180, `ARGB_8888` вместо `RGB_565`, JPEG 85: на полосе перемотки в плеере кадры были мыльными. ~0.7 МБ на фильм вместо ~0.2 и вдвое дольше генерация. Спрайты старого формата пересоздаются сами - `IllusionApplication.generateThumbnailIfMissing` сверяет `frameWidth` с `ThumbnailGenerator.FRAME_WIDTH`.

**Громкость телевизора при трансляции** (added 2026-09-20) — ползунок в панели трансляции плюс перехват аппаратных кнопок громкости, пока идёт каст (`PlayerScreen`'s `PlayerKeyEvents` handler → `PlayerViewModel.castAdjustVolume`, шаг 5%): локальное воспроизведение в этот момент на паузе, поэтому качелька должна двигать ТВ, а не молчащий динамик телефона. Google Cast — громкость устройства через `CastSession.volume`; DLNA — сервис RenderingControl (`SetVolume`/`GetVolume`, канал Master), чей controlURL теперь тоже вытаскивается из device description (`DlnaDevice.renderingControlUrl`, null если сервиса нет — тогда ползунок просто не показывается). Текущее значение забирается тем же опросом раз в 2 с, чтобы ползунок не расходился с ТВ, если громкость покрутили его собственным пультом. **Не проверено на устройстве.**

**Сцена после титров** (added 2026-09-20, `MediaItemEntity.postCreditsStartMs` + `MIGRATION_21_22`) — для фильмов Marvel и прочих, где после титров есть ещё кусок. Отметка ручная и **по одному элементу**, а не по сезону, как интро: это свойство конкретного фильма, и автодетект тут неприменим — сравнивать не с чем, соседней серии нет. Отмечается в панели ⚙ плеера («Сцена после титров»), во время титров показывается баннер «К сцене после титров» (`PlayerViewModel.isBeforePostCredits`: окно от отметки начала титров, либо, если её нет, за 8 минут до самой сцены). Пока сцена впереди, баннер «Пропустить титры» намеренно не показывается — иначе он уводил бы к следующей серии ровно мимо того, ради чего метка и ставилась.

**Установка обновлений видна в настройках** (added 2026-09-20) — Настройки → Обновления → «Установка обновлений» показывает, выдано ли разрешение «установка неизвестных приложений», и кнопку «Разрешить установку». Раньше о нём узнавали только в момент установки, когда приложение внезапно уводило в системные настройки (жалоба пользователя). Статус пересчитывается на каждом ON_RESUME, потому что выдаётся он за пределами приложения.

**Тихое обновление приложения** (added 2026-09-20, `data/update/UpdateInstaller.installSilently` + `UpdateInstallReceiver`) — по жалобе «каждое обновление показывает предупреждение безопасности» (у пользователя это были скан HyperOS и Play Protect, оба цепляются за открытие системного установщика). Вместо `Intent.ACTION_VIEW` обновление теперь коммитится как сессия `PackageInstaller` с `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` (API 31+) и разрешением `UPDATE_PACKAGES_WITHOUT_USER_ACTION` — ровно то, чем пользуются магазины вне Play (RuStore и прочие). Тихо проходит только self-update и только если предыдущую версию поставило это же приложение, поэтому ПЕРВОЕ обновление после выхода этой сборки всё ещё покажет системный диалог, а следующие — нет. `setRequestUpdateOwnership` (API 34) НЕ используется: lint поймал, что ему нужно привилегированное `ENFORCE_UPDATE_OWNERSHIP`, недоступное обычному приложению. Одноразовый гейт «установка неизвестных приложений» остаётся обязательным для обоих путей. Результат сессии приходит в `UpdateInstallReceiver`: `STATUS_PENDING_USER_ACTION` → запускаем присланный Intent (это и есть запасной путь), отказ → диалог с причиной от системы; успех не обрабатывается, потому что процесс в этот момент заменяется. Если сессия не создалась — откат на старый `installIntent`. **Предупреждение при установке - это Google Play Защита, а не прошивка** (уточнено пользователем 2026-09-21). Play Protect предупреждает о приложениях, которых нет в Play и которых он не знает по подписи/хешу - то есть о КАЖДОЙ новой версии этого приложения; популярные APK с GitHub (пример пользователя - ChutterUI) он уже знает и пропускает молча. Из кода это не отключается: публичного API нет, и «правильного» способа стать известным Play Protect, кроме публикации в Play, не существует. В Настройках → Обновления рядом с разрешением на установку лежит пояснение и кнопка, открывающая настройки Play Защиты (цепочка интентов: `VerifyAppsSettingsActivity` из `com.google.android.gms` → страница сервисов Google Play в Маркете → системная безопасность → общие настройки, каждый проверяется через `resolveActivity`, потому что на устройстве без сервисов Google первых двух нет).

**Итог по тихой установке (2026-09-21): на HyperOS она не работает, и приложение перестало на ней настаивать.** После отказа прошивки ставится флаг `SettingsRepository.silentInstallRejected`, и дальше обновление сразу идёт через обычный системный установщик - без попытки, которая всё равно закончится отказом (пользователь видел ошибку перед установкой, а после повтора всё ставилось). Приложение на это повлиять не может. Отдельно починено: уведомление об обновлении висело в шторке и после установки («пришло уведомление, хотя я уже установил») - `UpdateNotifications.cancel` вызывается и при `UpToDate`, и на старте `UpdateViewModel`, если версия из `lastNotifiedUpdateVersionCode` уже установлена.

**Remaining real gaps**:
1. ~~Cast/DLNA not implemented~~ — DLNA casting built 2026-09-19 (see Key decisions), not yet verified against a real TV. Chromecast/Cast SDK remains deliberately unimplemented.
2. ~~Audio-fingerprint auto-skip-intro detection~~ — built 2026-09-19 (`data/intro/*`, `work/IntroDetectWorker`, button in the player's ⚙ panel under the manual marker). Haitsma-Kalker fingerprints (own radix-2 FFT, 32 log bands 300-3400 Hz, 32-bit hash per 64 ms frame at 8 kHz mono) of the first 5 minutes of this episode and a neighbouring one in the same season, best-offset match with ≤8 bit errors per frame, longest run (gaps ≤1.3 s bridged) becomes the intro range and is written to the whole season via the new `LibraryRepository.markIntroRange` (a detected intro can start after a cold open, unlike the manual path's assumed 0). Audio is decoded by platform MediaCodec over `SmbMediaDataSource`, so a DTS/TrueHD/WMA track simply reports "не удалось" rather than dragging the FFmpeg audio path into a worker. Runs as a unique WorkManager job (minutes of SMB traffic per run - MediaExtractor pulls the container's video bytes past the audio it wants). Pure-Kotlin half covered by `IntroMatcherTest` (FFT vs naive DFT, synthesised shared theme found at the right offset, unrelated episodes and too-short jingles rejected). **Verified on a real series 2026-11-15** (AAC stereo .mp4): intro found at 2:15-2:55, boundaries confirmed by the user; two other series with only a 3-5 s title sting correctly reported "not found" (66/80 matching frames against the 156-frame = 10 s minimum - that floor is deliberate, don't lower it to catch stings). The same day it got ~9x faster (2 min 36 s -> 18 s per season): `SmbMediaDataSource` used to send one SMB READ per extractor request, i.e. per audio sample. It now reads through FOUR 256 KiB windows (LRU). Four and small on purpose - a first attempt with a single 1 MiB window made it 3.5x SLOWER (4.5 min per episode), because the platform MP4 extractor alternates between the sample data and the sample tables in `moov` on every sample, so one window was refilled on every read; and a big window drags the interleaved video along for nothing. Don't "simplify" it back to one buffer. `ThumbnailGenerator` reads through the same class (speed-up there not measured). The whole-series run (each season compared within itself, seasons that already have markers skipped) is the only mode now and is started from the series' Details screen - see «Весь автопоиск живёт в карточках» below. `IntroDetector`/`IntroAudioDecoder` now log to logcat (track format, seconds decoded, best offset/score, longest run) - the first real run failed with no way to tell why.
3. ~~MatroskaExtractor Cues-table hang on pathological `.mkv` files~~ — **seeking restored 2026-09-14, the hang itself is still Media3's.** On a few very large files (the 38 GB "Аватар: Путь воды" remux) Media3's own "jump to the Cues at the end, then back" leaves the player buffering forever: the loader opens the file at the Cues offset and never reads (root cause inside Media3 not localized). `PlayerViewModel`'s stall watchdog (30 s, first play) still detects that per file and remembers it (`SettingsRepository.cuesSeekWorkaroundStableIds`); those files get `FLAG_DISABLE_SEEK_FOR_CUES` — which on its own makes the whole file `SeekMap.Unseekable` (bytecode-verified) — **plus** `data/player/mkv/OutOfBandCuesExtractor`, wired in `IllusionExtractorsFactory`. The wrapper intercepts that unseekable seek map and replaces it with a `ChunkIndex` built from the Cues read over a *separate* `DataSource` by `MatroskaCuesReader` (EBML walk: SeekHead incl. a second SeekHead, TimecodeScale, Cues; skips Tracks/Chapters/Attachments by size, never downloads them) — same primary-track cues and absolute Cluster positions as Media3's own `MatroskaSeekMap`, so seeking goes through `MatroskaExtractor.seek()` like any ordinary .mkv. Ordinary files are untouched. Covered by `MatroskaCuesReaderTest` (FFmpeg-muxed fixture: every cue lands exactly on a Cluster ID in the file bytes). Verified on-device: Аватар resumes at 53:49 and seeks to 2:19:21 (5775 cue points, "Seeking restored" in logcat). The ~2.5 s play / ~3 s rebuffer sawtooth it still had was NOT Wi-Fi or this wrapper (the wrapper only runs at open): `SmbDataSource` sent one SMB READ per Media3 `read()`, and Media3 asks for ~4.6 KiB per read, so throughput was capped by round trips (~12 Mbit/s over a 688–1297 Mbps link, 5 ms RTT to the router). Fixed 2026-09-14 with a 1 MiB read-ahead buffer in `SmbDataSource` (smbj clamps each READ to min(1 MB config buffer, negotiated maxReadSize), short reads handled; chunk capped by `bytesRemaining` so small bounded opens don't over-read): measured on-device 28–30 Mbit/s, ~90 READs/5 s at 12–15 ms each, zero rebuffers over 60 s, 6–27 s buffered ahead. The native libavformat demuxer idea is no longer needed for this.

Лишние секунды музыки из титров - осознанная цена.

Там же подтверждена слепая зона: настоящая первая сцена (2:25:44) тёмная и идёт до чёрной прокрутки, начало титров встало внутри неё (2:26:58) - только ручная отметка, причём ПОСЛЕ автопоиска (он затирает ручные сцены, если нашёл свои). Поиск всегда идёт по ВСЕМУ сериалу: `IntroDetectWorker` принимает `series_id`, уникальная работа на сериал и вид (`intro_detect_<id>` / `credits_detect_<id>`, политика KEEP). Заставка пропускает сезоны, где метки уже стоят (перепроверить сезон = сбросить его метку в плеере); титры ищутся заново во всех сериях. **Автопоиск заставки после сканирования** (2026-11-16): `LibraryScanWorker` берёт `result.newlyAddedStableIds`, через `LibraryRepository.getSeasonsOf` получает сезоны, в которых появились новые серии, кладёт их в `AutoIntroQueue` (файл `filesDir/auto_intro_queue.txt`) и ставит `IntroDetectWorker` с `KEY_AUTO_QUEUE` (уникальная работа `auto_intro_detect`, `APPEND_OR_REPLACE`). `drainQueue` разбирает очередь по сезону: сезон с меткой или из одной серии просто выбрасывается (вторая серия потом поставит его снова), запись удаляется только после обработки - убитый процесс продолжит с того же места. Почему файл, а не входные данные WorkManager: первый скан большой библиотеки даёт сотни сезонов, это не лезет в ~10 КБ. Почему всегда `Result.success()`: провал отменил бы работы, добавленные следом через APPEND. Выключатель - Настройки, рядом с пересканированием: «Искать заставки после сканирования» (`SettingsRepository.autoIntroAfterScan`, по умолчанию включён). Проверено на устройстве на сгенерированном сериале: «2 new items in 1 seasons» -> заставка найдена за 10 с. Номер сезона сканер раньше брал только из .nfo, и на этом была потеряна первая проверка (тестовые серии без .nfo дали «1 new items in 0 seasons») - с 2026-11-16 есть запасной разбор имени, см. ниже. Тестовые серии с общей «заставкой» генерируются ffmpeg (розовый шум с разным seed + общий `aevalsrc`-фрагмент) плюс `.nfo` с `<season>`/`<episode>`.

**После сканирования ищутся и титры** (2026-11-16): `drainQueue` после заставки вызывает `detectSeasonCredits(onlyUnmarked = true)` - ищет титры только у серий без метки и снимает отпечатки только с них и их соседей, чтобы сезон с одной новой серией в неделю не перечитывался с NAS целиком. Там же закрыт пробел: метки заставки пишутся сериям, существовавшим на момент поиска, и новая серия уже отмеченного сезона оставалась без метки - теперь диапазон копируется на весь сезон заново. Выключатель один, «Искать заставки и титры после сканирования». Проверено на сгенерированном сериале.

**Сезон и серия из имени файла и папки** (2026-11-16, `data/scan/SeasonEpisodeParser.kt`, `SeasonEpisodeParserTest`): когда .nfo их не дал, `LibraryScanner` берёт их из пути - `S01E03`/`1x03` в имени, папки `Season 1`/`Сезон 1`/`S01`/`1 сезон`, `E03`/`Серия 3`/`3 серия`, число в начале имени только внутри папки сезона. .nfo всегда главнее. Применяется и на быстром пути «файл не менялся» (это чистая работа со строками), поэтому уже проиндексированные серии получают сезон при обычном пересканировании. **Ловушка, уронившая скан на устройстве**: первая версия задавала нечувствительность к регистру встроенным `(?iu)` - все JVM-тесты прошли, а на телефоне скан завершился FAILURE; после замены на `RegexOption.IGNORE_CASE` прошёл. Движок регулярок на Android - ICU, не JDK; само исключение поймано не было (тогда оно не писалось в журнал - теперь `LibraryScanner` логирует исключение источника, `LibraryScanWorker` - итоговое сообщение). Вывод шире регулярок: зелёные JVM-тесты не доказывают, что код с `java.util.regex` работает на устройстве.

**Окно поиска титров - не больше 30% длины серии** (`decodeWindow`, `fromEnd`): с фиксированными 5 минутами серия короче окна целиком попадала в свой «хвост», и поиск титров находил общую ЗАСТАВКУ и помечал её как титры (поймано на 3-минутных тестовых сериях; короткий мультфильм дал бы то же). На 40-минутных сериях окно по-прежнему 5 минут.

**Сканирование удаляет пропавшие файлы** (2026-11-16, `LibraryScanner.pruneVanished`, `MediaItemDao.deleteVanished`): до этого сканер только добавлял и обновлял, и удалённый с NAS сериал оставался в библиотеке карточками-заглушками после любого числа пересканирований, включая полные (жалоба пользователя; та же находка стояла в аудите 2026-09-28, но тогда закрыли только удаление источника). Теперь после ПОЛНОГО обхода источника (любой сбой листинга бросает исключение раньше, так что «не увидели» значит «нет») элементы без файла удаляются вместе с прогрессом, избранным и спрайтами. Элемент со скачанной копией не трогается. Перенос/переименование не затронуты - stableId считается по содержимому, строка просто получает новый путь. Две защиты, потому что вместе с карточкой уходят метки и прогресс, не убирать: (1) обход не нашёл НИ ОДНОГО видео - так выглядит не смонтированный USB-диск на роутере, библиотека остаётся, скан сообщает об этом; (2) обычный скан потерял больше половины источника (от 20 элементов) - карточки остаются с пояснением, удаляет только полное пересканирование. Проверено на устройстве: удалено 67 элементов из ~3270. **Что убрано, видно пользователю**: `ScanResult.removed` (`RemovedTitle`, сериал - одна строка с числом серий) идёт в итоги скана (`KEY_REMOVED*`, блок «Этих файлов больше нет на сервере» в `ScanProgressScreen`, первые 40 названий), в текст уведомления и целиком в logcat. Первая версия писала в журнал только число, и на вопрос пользователя «как я узнаю, что пропало?» про те 67 ответить было нечем - не убирать этот отчёт.

**Аудит 2026-11-17, четыре правки в сканере и автопоиске** (unit-тесты прошли; сохранение меток при полном пересканировании и перенос файла (переименована папка: 0 новых, 0 убранных, прогресс на месте - 2026-11-20) проверены пользователем на устройстве, пункты 3-4 - **нет**; `MigrationTest` в тот же день прошёл на телефоне, все три миграции 21→24): (1) `LibraryScanner.scanSource` переносит в пересобранную строку то, что записало само приложение (`dateAdded`, метки заставки/титров/сцен) по `existingById` - до этого `toMediaItem` на медленном пути строил строку с нуля, и ПОЛНОЕ пересканирование стирало все метки библиотеки, а правка .nfo или перенос файла - метки этого тайтла. Новое поле `MediaItemEntity`, которое пишет приложение, а не скан, надо добавлять и туда. (2) Пропавшие считаются по stableId, а не по пути: по пути перенесённый файл (тот же id, новый путь) удалялся тем же сканом вместе с прогрессом и избранным и возвращался голым на следующем, а файл, заменённый другим по тому же пути, оставлял старую строку навсегда. Прежняя фраза выше «перенос/переименование не затронуты» была неверна до этой правки. ## Working conventions

- **Communicate in Russian** on this project (user's explicit preference).
- **No abstractions beyond what's needed** — match the existing no-DI, minimal-layering style.
- When listing deferred/unimplemented items, expect the user's answer to be "do it now" — don't just leave gaps noted, offer to implement.
- **Verify on the real device** (Xiaomi 17 via `adb`) rather than asserting something "should work," especially for player/HDR/DV/PiP behavior that can't be confirmed from code alone.
- For fast-moving/lightly-documented APIs (newer Media3 Effects, newer Android platform permissions), check real signatures/official docs before writing code — don't rely on training-data recall, since Android has moved past the knowledge cutoff.

# Правила экономии токенов

## Общий стиль ответов
- Кратко и по делу. Развёрнутые объяснения — только если явно попросили "объясни подробно" или "распиши почему".
- Не пересказывай код, который только что написал/поправил — показывай сам патч/diff, без словесного дублирования.
- Не повторяй условие задачи и не резюмируй то, что уже есть в предыдущем сообщении.
- План — 2-4 пункта максимум, без пространных рассуждений в самом ответе.

## Работа с файлами
- Не перечитывай файл, если он уже есть в контексте и не менялся с последнего чтения.
- Для точечной правки используй edit/patch по конкретному фрагменту, а не полную перезапись файла.
- Если нужен только кусок файла (функция, класс) — ищи grep'ом/по имени символа, не читай файл целиком.
- Не открывай директорию целиком "на всякий случай" — сначала уточни, какой именно файл нужен.

## Инструменты и сборка
- Объединяй мелкие правки в один проход, а не вызывай инструмент правки на каждую строку отдельно.
- Тесты/сборку запускай один раз после завершения логического блока правок, а не после каждого шага.
- Полную сборку Android APK — в самом конце; по ходу работы используй быстрые unit-тесты или компиляцию отдельного модуля.

## Уточнения
- Если без уточнения велик риск переделки — задай один конкретный вопрос, вместо того чтобы предполагать несколько сценариев сразу и писать код под каждый.

## Контроль лимита сессии
- Если появляется предупреждение, что осталось ≤10% лимита 5-часовой или недельной сессии — сразу сообщи об этом явно и предложи один из вариантов:
  1. зафиксировать текущий прогресс коммитом;
  2. доделать только критичный минимум, чтобы новый APK собрался и встал на телефон;
  3. отложить второстепенные правки на следующую сессию.
